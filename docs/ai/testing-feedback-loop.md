# Testing Feedback Loop

이 문서는 테스트, 빌드, 린트, CI 실패를 AI와 함께 확인하고 수정할 때의 반복 흐름입니다.

## 기본 흐름

1. 실패한 명령과 핵심 에러를 먼저 확인합니다.
2. 프론트, 백엔드, Docker, CI 중 어느 범위의 실패인지 구분합니다.
3. 원인을 단정하지 않고 가능한 원인과 확인 방법을 나눕니다.
4. 수정은 실패와 직접 관련된 최소 범위로 진행합니다.
5. 같은 검증 명령을 다시 실행해 수정 결과를 확인합니다.
6. 다시 실패하면 새 에러인지 같은 에러인지 구분하고 다음 확인 항목을 보고합니다.

## 확인할 정보

```text
실패한 명령:
실패한 위치:
핵심 에러:
최근 변경 파일:
재현 방법:
기대 결과:
```

## 프론트 검증 실패

- build 실패인지 lint 실패인지 먼저 구분합니다.
- 라우트, import 경로, 컴포넌트 분리 후 경로 변경 여부를 확인합니다.
- CSS 변경 후에는 화면 깨짐, 텍스트 겹침, 반응형 영향을 확인합니다.
- Vite/Rollup optional dependency 오류는 의존성 재설치 여부를 별도 확인합니다.

## 백엔드 검증 실패

- 문법 오류, 라우터 연결 오류, Swagger 문서 오류, DB 연결 오류를 구분합니다.
- API 변경 시 request/response 구조와 Swagger 문서가 함께 맞는지 확인합니다.
- Prisma 변경이 있으면 schema, migration, seed, 실제 DB 영향 범위를 나눠 봅니다.
- 인증/권한 실패는 토큰 흐름과 보호 라우트 영향을 함께 확인합니다.

## CI 실패

- 로컬 `npm run ci`와 GitHub Actions 결과가 같은지 비교합니다.
- 디렉터리 구조가 바뀐 경우 루트 `package.json` 스크립트와 `.github/workflows/ci.yml`을 확인합니다.
- CI에서만 실패하면 Node 버전, lock 파일, optional dependency, 환경변수 차이를 확인합니다.
- 실패 로그 전체를 붙여넣기보다 핵심 에러와 직전 명령을 우선 공유합니다.

## 라이다 연동 테스트

- 조선대 측 데이터 규격이 확정되지 않은 경우 mock 실패와 실데이터 실패를 구분합니다.
- 원본 payload 수신 실패, adapter 변환 실패, 이벤트 저장 실패를 나눠서 확인합니다.
- 필드 의미가 불확실하면 임의 확정하지 말고 `확인 필요`로 남깁니다.
- 현장 연동에서는 IP, 포트, 방화벽, API URL, 호출 주기, replay 가능 여부를 함께 확인합니다.

## 결과 보고

```text
실패 원인:
수정 파일:
변경 내용:
재검증 명령:
재검증 결과:
남은 리스크:
```

검증하지 못한 항목은 `미검증`으로 표시하고 이유를 적습니다.
