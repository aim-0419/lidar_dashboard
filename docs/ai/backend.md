# Backend

백엔드는 기존 계약 유지가 우선이다.

> 최종 업데이트: 2026-09-03

- API 경로, 메서드, 응답 구조 변경은 승인 후 진행한다.
- 포트, env 이름, DB 스키마, 마이그레이션 변경은 승인 후 진행한다.
- 에러 응답 형식과 상태 코드는 기존 패턴을 따른다.
- 외부 장비, 파일 경로, 네트워크 의존성은 확인 전 단정하지 않는다.
- 로그에는 비밀값과 과도한 원본 데이터를 남기지 않는다.
- 변경 후 가능한 API 스모크 체크를 수행한다.

## 라우터 인증·권한 리뷰

- 개별 API의 권한 검사만 보고 접근 가능 여부를 단정하지 않는다.
- `app.js -> routes/index.js -> 도메인 라우터 -> controller` 순서로 실제 요청 경로를 추적한다.
- 상위 `app.use` / `router.use`의 경로, 등록 순서, 앞서 실행되는 인증·역할 검사를 함께 확인한다.
- 경로 없이 등록한 도메인 라우터의 `router.use(requireRole(...))`는 다른 도메인 요청도 차단할 수 있다. 도메인 전용 권한 검사는 해당 API에 직접 붙이거나 도메인 경로로 범위를 제한한다.
- 프론트 메뉴·편집 UI와 백엔드 권한 정책을 맞추되, 조회 권한과 수정·제어 권한을 구분한다.
- `SUPER_ADMIN`, `MANAGER`, 미인증 요청을 상위 라우터에 통과시켜 검증한다. 개별 미들웨어 모의 테스트나 빌드 통과만으로 실제 API 접근이 검증됐다고 보고하지 않는다.
- 재현 및 검증 절차는 [Testing Feedback Loop](testing-feedback-loop.md)의 인증·권한 회귀 검증을 따른다.

## Redis 사용 원칙

- Redis는 실시간 관제 화면을 위한 캐시로 사용한다.
- PostgreSQL을 대체하는 영구 저장소로 사용하지 않는다.
- 최신 라이다 payload, 현재 objects 배열, 최근 이벤트, 장비 연결 상태처럼 짧게 유지해도 되는 데이터만 Redis에 둔다.
- Redis key에는 `lidar:latest:{source}`, `lidar:objects:{source}`, `events:recent`처럼 목적과 source를 드러내는 이름을 사용한다.
- 최신 상태 key에는 TTL을 설정한다. 예: 5~10초.
- 역주행, 보행자 진입/이탈, 상황 종료처럼 이력으로 남겨야 하는 데이터는 PostgreSQL에 저장한다.
- 매초 들어오는 정주행 objects 전체를 PostgreSQL에 원본 그대로 계속 저장하지 않는다.
- Redis 장애 시에도 이벤트 저장 API가 완전히 실패하지 않도록 PostgreSQL 저장 흐름과 캐시 갱신 흐름을 분리한다.
